# 调度算法设计说明

本文档记录 `planner.py` 中行程编排算法的设计推导，以及关键参数的扫描实验记录。

## 问题定义

输入：
- 景点池 `spots[]`：每个点有名称、类型、评分、坐标、建议时长
- 天数 `days`
- 起点日期

输出：
- `days` 个日区块，每块含 2~4 个景点
- 约束：同一天内景点地理邻近；招牌景点不能遗漏；总天数不能超

这是一个**带约束的聚类 + 装箱**问题。理论上是 NP-hard（可以归约到带容量的 k-median）。

但实际场景有几个可利用的结构：
1. 天数少（3~7 天），搜索空间不大
2. 景点天然按片区聚集（古城、近郊、远郊）
3. 用户对"最优"的容忍度高——只要动线合理、招牌不漏，就是好行程

所以选择**带领域知识的贪心**，而不是精确求解。

## 迭代过程（失败路线记录）

### 尝试 1：轮询分配

```
day = idx % days
```

**结果**：灾难性。景点按分数排序后轮询，导致鲁迅故里（D1）、安昌古镇（D2）、东湖（D3）轮流出现，每天跨半个城市。

**教训**：不能用"序号"分配，必须用"地理"分配。

### 尝试 2：整片区分配 + 负载均衡

按区域聚类，然后按区域总分排序，逐个区域整块塞给"当前景点最少的那天"。

**结果**：还是乱。D3 同时出现城东和柯桥（相距 20 公里）。

**原因**：负载均衡只看数量，不看地理。某天只有 1 个点，就被塞进了远在柯桥的片区。

### 尝试 3：贪心最近邻合并

每次把"距离最近的两块"合并，直到块数 = 天数。

**结果**：部分改善。D2 正确合并了兰亭 + 柯桥。

**新问题**：块数初始 = 区域数（11 个），要合并到 5 个，意味着强行合并 6 次。远郊（新昌、上虞、诸暨）被合并后占据了 3 天，古城区反而挤在 1 天里。

**教训**：合并的方向错了。应该"从高分片区往下填"，而不是"把低分片区往上并"。

### 尝试 4：价值密度 + 配额（当前方案）

四阶段：

**阶段 0 · 名片保底**
`MUST_SEE` 里的城市名片无条件入选。

为什么需要这一步？因为评分体系依赖检索文本里的"4A/5A"标注。兰亭的检索文本里没有这个标注，得分只有 2.50（与东湖的 3.00 差距不大，但实际重要性差很远）。纯靠打分会让名片落选。

名片还需要**地理聚类分组**：离城最远的先分组（它最挑天），后续名片找"与已有组成员距离最小"的组加入，超过 `MAX_DAY_SPAN_KM` 就另开一组。这样"柯岩+兰亭"会在一组（相距 5.6km），"五泄"自己一组（距柯岩 49.7km）。

**阶段 1 · 片区配额**
计算每个片区的"价值密度"：

```
top_score = 该片区得分最高的 per_day 个点之和
val = top_score + (有招牌点 ? 2.5 : 0) + REGION_BONUS
need = ceil(片区点数 / per_day)
density = val / need - 离城距离 × 0.28
```

取前 `per_day` 个点而非全部，是为了防止噪声点拖累好片区。兰亭片区里混进了"汤江岩风景区"（-1.50）和"枫桥古镇"（-3.50）两个噪声点——它们实际不在兰亭附近，是检索误判。如果按片区总分算，兰亭片区是 -2.5 分，直接出局。

按 density 排序，给正密度的片区各留 1 天配额；密度超过最高值 55% 且点位多的片区多留 1 天。

**阶段 2 · 配额执行**
按 density 从高到低，为每个片区挑天。优先填"已有本片区点的天"（成组），其次填空天。

**阶段 3 · 全局补位**
剩余容量按全局分数降序填。每天受 `per_day` 和 `MAX_DAY_SPAN_KM` 双重约束，装不下的进备选。

### 关键 bug：距离锚点

早期版本用 `assign_region(片区中心)` 的返回值当"离城距离"：

```python
dist = assign_region(clon, clat)[1]     # 错！
```

`assign_region` 返回的是"距离最近的区域中心有多远"。对片区自己的中心调用，永远返回 0。

结果：所有片区的距离惩罚都是 0，"远郊降权"完全失效。

修复：

```python
CITY_CENTER = (120.578, 30.000)          # 市中心锚点
dist = haversine(clon, clat, *CITY_CENTER)  # 正解
```

**这个 bug 隐藏得很深**——代码跑得通、没有报错、结果看起来"差不多对"，只是远郊景点偶尔混进主行程。靠打印中间变量才发现。

## 参数扫描记录

在绍兴样本（62 个景点，80 条检索结果）上扫描：

### PER_DAY（每天主景点数上限）

| 值 | 结果 |
|---|---|
| 2 | 古城占 5 天，只排 10 个点，招牌大量流失 |
| 3 | 古城占 5 天（鲁迅故里 + 仓桥直街 + 书圣故里 / 八字桥 + 周恩来纪念馆 + 蔡元培故居 / …），东湖、柯岩、兰亭全丢 |
| **4** | **古城 3 天 + 郊野各归其位，20 个点，招牌全在** |
| 5 | 出现跨片区硬拼（兰亭 + 五泄同天） |

**选 4。**

### 距离系数

| 值 | 结果 |
|---|---|
| 0.10 | 远郊片区也能拿到配额，新昌/上虞占据 2 天 |
| 0.20 | 与 0.28 接近，但 D2/D5 顺序不稳定 |
| **0.28** | **稳定：市区优先、远郊自动降级** |
| 0.40 | 古城内部都开始互相排斥（古城北与古城核心分开），过度惩罚 |

**选 0.28。**

### MAX_DAY_SPAN_KM

| 值 | 结果 |
|---|---|
| 12 | 东湖（离古城 4.5km）与大禹陵（2.8km）能和古城同天，但柯岩片区被拆散 |
| **18** | **柯岩+兰亭（5.6km）、安昌+柯桥（4.4km）都能成组** |
| 30 | 五泄（52km）以外的点全都能拼，失去约束意义 |

**选 18。**

### FAR_SIGNATURE_KM

| 值 | 结果 |
|---|---|
| 25 | 柯岩（10.4km）、兰亭（8.4km）都算远郊，被降级——太激进 |
| **45** | **只降级五泄（52km）、新昌大佛寺（64km）** |
| 60 | 全部保留，五泄挤进主行程 |

**选 45。** 注意这个阈值是**产品决策**而非算法必然：单程 1.5 小时以上的景点，当天往返会挤掉市区深度体验。跑 6 天时五泄能自然回归。

## 天数敏感性验证

同一份景点池，只改 `--days`：

| 天数 | 主行程景点 | 构成 |
|---|---|---|
| 3 | 12 | 古城 3 天填满，柯桥 + 柯岩 + 兰亭挤 D3 |
| 4 | 16 | 追加古城北街区（周恩来纪念馆等） |
| 5 | 20 | 追加古城核心深度（府山公园、大善塔、博物馆） |
| 6 | 21 | 五泄自动回归填补空档 |

**单调递增且无跳变**，说明算法对天数参数是连续的、可预期的。

## 为什么不用大模型

行程规划的瓶颈是**数据质量**和**地理约束**，不是语言理解：

- 数据质量：需要判断"这条信息来自权威媒体还是三年前的论坛帖"——规则比模型更稳定
- 地理约束：需要保证同天景点 ≤ 18km——这是确定性计算，模型反而容易算错

规则引擎的优势：
- 可复现（同输入同输出）
- 可调试（每个决策都有中间变量可查）
- 零成本、离线可跑
- 快（编排耗时 < 1 秒）

**大模型适合插入的位置**是"抽取层"——处理非标准表述（例如"离鲁迅故里两站路的那个老台门"）。`extract.py` 的输出格式与模型输入一致，替换是局部的。

## 已知局限与改进方向

1. **坐标表手工维护**：未收录的景点落到"未定位"，评分 -2.0，通常进备选。可接入高德 POI 自动反查。
2. **不支持多目的地**：目前单城市模型。跨城游需要拆成多次调用后手工拼接。
3. **时间窗未建模**：没考虑"沈园夜场 19:00 才开""博物馆周一闭馆"。可以加 `open_hours` 字段后扩展阶段 3 的填充逻辑。
4. **用餐建议是模板**：`MEAL_TEMPLATES` 按片区套用，不是真实店铺。真实店名需从检索结果的"美食"查询里另取。
