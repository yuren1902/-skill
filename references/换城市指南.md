# 换城市指南

这个 skill 的**算法层是通用的**，但有三处城市相关的数据表需要替换。本文档说明替换步骤。

## 需要替换的三处

| 位置 | 文件 | 内容 | 数据量 |
|---|---|---|---|
| 坐标表 | `planner.py` → `KNOWN_COORDS` | 景点名 → (经度, 纬度) | 30~60 条 |
| 区域表 | `planner.py` → `REGIONS` | 功能分区 + 中心坐标 + 半径 | 8~15 条 |
| 名片清单 | `planner.py` → `MUST_SEE` | 城市必去景点 | 8~15 条 |

另外建议同步更新：

| 位置 | 文件 | 内容 |
|---|---|---|
| 地点白名单 | `extract.py` → `KNOWN_SPOTS` | 提高抽取置信度 |
| 父子关系 | `planner.py` → `PARENT_CHILD` | 避免子景点重复占位 |
| 行程外清单 | `planner.py` → `OFFROUTE_EXACT` | 排除客源地/邻市景点 |
| 中心锚点 | `planner.py` → `CITY_CENTER` | **必须改**，否则距离计算全错 |

## 步骤

### 第 1 步：确定城市中心锚点

`CITY_CENTER` 是所有"离城距离"计算的基准。取**老城核心区**（不是行政中心，不是几何中心）。

例如：
- 绍兴 → `(120.578, 30.000)`（鲁迅故里一带）
- 苏州 → `(120.622, 31.309)`（观前街一带）
- 泉州 → `(118.589, 24.909)`（西街一带）

**坐标系必须是 GCJ-02**（高德/腾讯用的火星坐标），不能用 WGS-84（GPS 原始）或 BD-09（百度）。混用会导致几百米的偏移，在这类"判断是否同片区"的场景下足以造成误判。

> 怎么判断拿到的是哪个坐标系？在高德地图上搜一个知名地点，看坐标。若与 GPS 读数接近则可能也是 GCJ-02（国内地图均为 GCJ-02）。anysearch 检索结果里的坐标通常来自高德，是 GCJ-02，可直接用。

### 第 2 步：划分功能分区

`REGIONS` 是"景点聚类"的骨架。划分原则：

1. **按游客的动线习惯分**，不按行政区分
2. 每个分区以"游客愿意在一天内步行/短驳往返"为尺度（半径 2~5 km）
3. 远郊单独成区，半径可以给大些（但中心坐标要准）

绍兴的分区可作为模板：

```python
REGIONS = [
    ("古城核心", 120.575, 30.002, 3.0),     # 半径3km，步行范围
    ("古城北",   120.580, 30.011, 2.5),
    ("古城西",   120.579, 29.988, 2.5),
    ("城东",     120.625, 29.998, 4.0),     # 东湖
    ("城南",     120.598, 29.982, 4.0),     # 大禹陵
    ("兰亭片区", 120.520, 29.943, 12.0),    # 西郊
    ("柯桥片区", 120.485, 30.100, 22.0),    # 西北，安昌古镇
    ("鉴湖柯岩", 120.470, 29.995, 14.0),    # 西南，柯岩
    ("黄酒小镇", 120.549, 30.040, 6.0),
    ("诸暨片区", 120.150, 29.715, 45.0),    # 远郊
    ("新昌片区", 120.900, 29.500, 65.0),
    ("上虞片区", 120.873, 30.025, 32.0),
]
```

**注意最后一个字段**（半径）目前算法里没实际使用——`assign_region()` 用的是"最近中心"判定，不看半径。保留它是为了未来支持"超过半径就算远郊"的逻辑。

**坐标要准**。绍兴调优过程中发现过：把"安昌古镇"的中心坐标写成 `(120.480, 30.030)` 时，它被判到"兰亭片区"（因为兰亭中心更近）——但实际安昌在柯桥区，与兰亭隔了 20 公里。改成 `(120.485, 30.100)` 后才正确归到柯桥片区。

### 第 3 步：汇总坐标表

`KNOWN_COORDS` 是 `景点名 → (经度, 纬度)` 的字典。

**数据来源**（按可靠性排序）：
1. 高德地图搜索 → 复制坐标（最准）
2. anysearch 检索结果里的坐标字段（已在 `build_place()` 里处理）
3. 百度百科的经纬度（粗，仅作兜底）

**必须覆盖的景点**：所有你预期会进主行程的点。未收录的点会落到"未定位"，评分 -2.0，通常进备选——**这是可控的降级行为**，不是错误。所以坐标表可以渐进完善：先跑一次，看哪些点落进备选而且你不想让它们落选，再补坐标。

名称要**支持常见变体**：

```python
KNOWN_COORDS = {
    "鲁迅故里": (120.5855, 30.0015),
    "兰亭": (120.5200, 29.9430),
    "兰亭景区": (120.5200, 29.9430),      # 变体同坐标
    "柯岩风景区": (120.4650, 29.9600),
    "绍兴柯岩": (120.4650, 29.9600),
    ...
}
```

### 第 4 步：定名片清单

`MUST_SEE` 里的点**无条件进主行程**，不参与打分竞争。

```python
MUST_SEE = {
    "绍兴": ["鲁迅故里", "沈园", "兰亭", "东湖", "大禹陵", "安昌古镇",
             "仓桥直街", "书圣故里", "柯岩", "柯岩风景区", "柯桥古镇",
             "黄酒小镇", "五泄", "五泄风景区", "八字桥"],
}
```

**挑选标准**：问自己"如果只去一个地方，是不是这个？"——是的话就放进清单。

**不要放太多**。名片会挤占主行程容量（每天 4 个位）。绍兴放 10 个点（去重后）刚好：3 天古城 + 1 天柯桥/柯岩 + 1 天古城北。如果放到 20 个，会互相挤压。

**放不下的会自动降级**：离城 > 45km 的名片（如五泄 52km、新昌大佛寺 64km）自动转入"一日游备选"。这是设计行为——想让它进主行程，把 `FAR_SIGNATURE_KM` 调大。

### 第 5 步：补充辅助表

**`OFFROUTE_EXACT`** —— 行程外地点。加两条：
- 客源地城市名（如"上海""上海虹桥"）
- 邻市知名景点（如从上海去绍兴时，"西湖""西塘古镇"常被检索带出来）

```python
OFFROUTE_EXACT = {
    "西湖", "杭州西湖", "西塘古镇", "乌镇", "周庄", "南浔古镇",
    "上海虹桥", "虹桥", "上海", "杭州", "杭州东", "绍兴北站",
    ...
}
```

**`PARENT_CHILD`** —— 父子景点。避免"鲁迅故里"和"三味书屋"同时占位。

```python
PARENT_CHILD = {
    "鲁迅故里": ["三味书屋", "百草园", "鲁迅故里步行街"],
    "柯岩风景区": ["鲁镇", "柯岩"],
    "仓桥直街": ["广宁桥", "东双桥", "白塔", "宝珠桥"],
}
```

**`KNOWN_SPOTS`**（在 `extract.py`）—— 抽取白名单，命中即 `confidence: high`，评分高 1.5 分。

```python
KNOWN_SPOTS = ["鲁迅故里", "沈园", "兰亭", "东湖", "大禹陵", ...]  # 34 个
```

## 第 6 步：跑一次并调参

```bash
cd scripts
python pipeline.py \
  --origin 上海 --city 新城市 \
  --days 5 --start 2026-10-01 \
  --out ./out

# 只看编排结果（跳过检索，调参时用）
python planner.py --places out/places.json --days 5 \
  --start 2026-10-01 --city 新城市 --out out/it5.json

# 多天数对比
for d in 3 4 5 6; do
  python planner.py --places out/places.json --days $d \
    --start 2026-10-01 --city 新城市 --out out/it$d.json
done
```

**验收标准**：
1. 每天景点同片区或紧邻片区（跨度 < 18km）
2. 名片清单里的点都在主行程（或明确标为一日游备选）
3. 天数是单调递增的（3 天 ≤ 4 天 ≤ 5 天 的景点数）
4. 没有明显噪声（客源地、邻市景点、设施名）

**如果第 1 条不满足**（出现跨片区硬拼）：检查 `CITY_CENTER` 是否设对，以及 `REGIONS` 的中心坐标是否准确。绝大多数问题是坐标错误导致的。

**如果第 2 条不满足**：往 `MUST_SEE` 里补点，或检查该点是否在 `places.json` 里（可能抽取层就没抽到）。

**如果第 3 条不满足**（天数增加景点数反而减少）：说明某个片区的 `REGION_BONUS` 给得太高，让它垄断了容量。按片区重要性调整。

## 参考：一个完整的替换示例

假设要移植到**苏州**：

```python
# 1. 中心锚点（观前街一带）
CITY_CENTER = (120.622, 31.309)

# 2. 分区
REGIONS = [
    ("古城核心", 120.622, 31.309, 3.0),     # 观前街/平江路
    ("古城西南", 120.590, 31.295, 3.0),     # 盘门/沧浪亭
    ("古城东北", 120.640, 31.320, 3.0),     # 拙政园/狮子林/博物馆
    ("虎丘片区", 120.575, 31.340, 6.0),
    ("吴中片区", 120.530, 31.250, 15.0),    # 木渎/天平山
    ("园区金鸡湖", 120.730, 31.310, 10.0),  # 现代园区
    ("同里古镇", 120.720, 31.160, 25.0),    # 远郊
    ("周庄古镇", 120.850, 31.115, 38.0),
]

# 3. 名片
MUST_SEE = {
    "苏州": ["拙政园", "苏州博物馆", "平江路", "山塘街", "虎丘",
             "留园", "狮子林", "网师园", "盘门", "同里古镇", "周庄古镇"],
}

# 4. 行程外（从上海出发）
OFFROUTE_EXACT = {
    "上海", "上海虹桥", "上海站", "虹桥", "苏州北站",
    "杭州", "西湖", "乌镇", "西塘古镇",   # 邻市常被带出
    "金鸡湖", "东方之门",  # 若不想排现代园区
}

# 5. 父子关系
PARENT_CHILD = {
    "拙政园": ["苏州园林"],
    "虎丘": ["虎丘塔", "剑池"],
    "同里古镇": ["退思园", "三桥"],
    "周庄古镇": ["沈厅", "张厅", "双桥"],
}
```

然后按第 6 步跑通、验收、调参。

## 常见问题

**Q：不补坐标表能跑吗？**
A：能。未定位的点会被降权（-2.0），通常进备选。如果落在备选的点你能接受，就不必补。但主行程会缺一些本该进来的点。

**Q：`REGIONS` 半径字段有什么用？**
A：目前没用（`assign_region` 用最近中心判定）。保留是为了未来支持更精细的归属判断。

**Q：多远算"远郊"？**
A：看 `FAR_SIGNATURE_KM`（默认 45km）。这是产品决策——单程 1.5 小时以上当天往返会挤掉市区体验。想更激进就调小，想更保守就调大。

**Q：能处理多城市联游吗？**
A：不能直接处理。拆成多次调用（如"上海→苏州"和"苏州→杭州"各跑一次），然后手工拼接成完整行程。算法本身是单目的地模型。

**Q：`MUST_SEE` 里放多少点合适？**
A：8~12 个。太少（<6）核心景点可能落选；太多（>15）会互相挤占容量，反而导致部分名片进不了主行程。

**Q：可以不改代码、只改数据就换城市吗？**
A：可以。三张表（`KNOWN_COORDS` / `REGIONS` / `MUST_SEE`）加上 `CITY_CENTER` 就是全部城市相关配置。算法层不需要任何改动。
